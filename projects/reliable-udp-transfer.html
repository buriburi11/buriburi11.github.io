The problem

UDP doesn't guarantee delivery: they can be lost, delayed, duplicated or reordered. The job was to move a file across UDP byte-for-byte anyway, through a proxy that deliberately drops, delays, jitters, reorders and rate-limits traffic, and to do it efficiently rather than one packet at a time.

That means rebuilding the core of TCP: a sliding window so many segments are in flight, cumulative ACKs, a retransmission timer that adapts to measured round-trip time, congestion control so the sender backs off when the network is lossy, and fast retransmit so a single loss doesn't cost a full timeout.

What I built and what was provided

This was Project 2 in a computer networks course. The instructor provided the proxy, the receiver, the test script, and the sender's startup, socket I/O and log formats. I implemented the sender's protocol logic:

MethodResponsibility
sendStep()One tick of the send loop: fill the window, check the timer, run timeout recovery, pick the next poll delay
fillWindow()Send while nextSeq < base + min(cwnd, maxWindow); start the timer when the flight goes from empty to non-empty
handleAck()Classify each ACK as advancing, duplicate or stale
handleAdvancingAck()Slide the window, take an RTT sample when Karn allows it, grow cwnd, restart or stop the timer
handleDuplicateAck()Count duplicates; on the third, halve ssthresh and retransmit once per loss
handleTimeout()Double the RTO, drop cwnd to 1, resend the whole flight
applyAckCredits()Slow start below ssthresh, additive increase above it
updateRtt()Jacobson/Karels smoothing and RTO clamping

Architecture and tradeoffs

Two threads share one lock. The main thread runs the send loop: fill the window, check the single DATA timer, then sleep 1–10 ms until the next deadline. A reader thread receives ACKs and updates the same state under that lock. Every field in the protocol state is guarded by it, so the sender's view of base, nextSeq and cwnd is always consistent.

One timer, not one per segment

Like TCP, there is a single retransmission timer for the oldest unacknowledged segment. It starts when the flight becomes non-empty, restarts whenever base advances, and stops when everything is acknowledged. On expiry the whole outstanding flight is resent. That's wasteful when only one segment was lost, but the receiver is Go-Back-N and would have discarded the later segments anyway.

Adaptive timeout, with Karn's rule

// first sample:   SRTT = R,  RTTVAR = R/2         (RFC 6298)
// later samples:  RTTVAR = (1-β)·RTTVAR + β·|SRTT - R|,  β = 1/4
//                 SRTT   = (1-α)·SRTT   + α·R,           α = 1/8
double calculatedRto = estimatedRttMs + 4 * deviationMs;
rtoMs = Math.max(MIN_RTO_MS, Math.min(MAX_RTO_MS, calculatedRto));   // 100 ms … 60 s

An ACK for a segment that was ever retransmitted produces no RTT sample, because there's no way to tell which copy it acknowledges. Using that sample could shrink the RTO while the network is congested.

Congestion control

cwnd starts at 1 and grows by one segment per ACKed segment in slow start, which doubles it every round trip. Above ssthresh it grows by one segment per full window. A timeout means heavy loss: ssthresh drops to half of cwnd and cwnd to 1. Three duplicate ACKs mean a single loss with data still flowing, so it's a milder cut: cwnd falls to the new ssthresh.

How I verified it

The provided script starts a receiver and proxy, runs my sender, and compares the received file byte-for-byte with the original. I ran it clean, then with targeted faults. This is long.bin (48 segments) with 15 ms of delay and segment 5 dropped once:

$ MAX_WINDOW=8 bash test-transfer.sh long.bin --delay-ms 15 --drop-data-once 5

ACK ack=4 rtt=34.682
CWND cwnd=6 ssthresh=64 phase=slow_start
DUP_ACK ack=4 count=1
DUP_ACK ack=4 count=2
DUP_ACK ack=4 count=3
FAST_RETRANSMIT seq=5
CWND cwnd=3 ssthresh=3 phase=congestion_avoidance
RESEND seq=5 reason=fast_retransmit
ACK ack=5
TIMEOUT base=6 resending=5 rto_before=100.000 rto_after=200.000
RESEND seq=6 reason=timeout
…
STATS segments_sent=48 retransmissions=6 dup_acks=5 timeouts=1 final_cwnd=8 avg_rtt=33.631
PASS: received bytes match long.bin

The trace shows each mechanism: slow start growing cwnd by one per ACK, the third duplicate triggering fast retransmit with the multiplicative decrease, and the RTO backing off from 100 to 200 ms on the timeout. It also shows the cost of a Go-Back-N receiver. Segments 6–10 had arrived but were thrown away, so they needed a second recovery.

Bugs I fixed

My first complete implementation, commit e88e848, had two bugs. Both were fixed in 19170ca. For this write-up I re-ran the earlier commit on the loss test above, to reproduce both.

Fast retransmit could never fire

The guard that limits fast retransmit to once per loss was inverted:

- if (duplicateAckCount == 3 && fastRetransmittedBase == base) {
+ if (duplicateAckCount == 3 && fastRetransmittedBase != base) {

fastRetransmittedBase starts at −1 and is reset to −1 whenever the window advances, so it never equals base and the branch never runs. Nothing crashes and the file still arrives, so a clean test run doesn't reveal it. Every loss waits for the full timeout instead. Because the second bug (below) crashes e88e848 before any loss happens, I isolated this one by running e88e848 with only the RTTVAR fix patched in. It logs five duplicate ACKs, no fast retransmit, and then:

DUP_ACK ack=4 count=3
DUP_ACK ack=4 count=4
DUP_ACK ack=4 count=5
TIMEOUT base=5 resending=6 rto_before=100.000 rto_after=200.000

The first RTT sample crashed the sender

On the first sample, updateRtt() set the smoothed RTT but left deviationMs, a Double, as null. The next line, estimatedRttMs + 4 * deviationMs, unboxed that null and threw a NullPointerException inside the ACK-reader thread. The send loop saw the reader's failure, and running e88e848 unmodified on the same test ends with Error: ACK reader failed. The fix initializes RTTVAR = R / 2, which is what RFC 6298 specifies.

What I would improve next

  • Selective acknowledgment. With a receiver that buffers out-of-order segments and reports SACK ranges, the loss above would cost exactly one retransmission instead of fast retransmit plus a timeout and five resends.
  • Fast recovery (NewReno). Inflating cwnd on each additional duplicate ACK would let the sender keep new data flowing while it waits for the retransmission's ACK.
