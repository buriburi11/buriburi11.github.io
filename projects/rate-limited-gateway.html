The problem

Model endpoints are expensive and shared, so something has to stand in front of them and decide who gets through. This gateway accepts plain-text chat requests over HTTP/1.1 and meters each caller against a per-minute limit: 3 requests for default callers, 10 for registered ones. Only approved requests are forwarded to the model.

What makes it non-trivial is that one request touches four different services, each with its own wire protocol, and the metering has to stay correct when many requests for the same caller arrive at the same instant.

  • Time, RFC 868: connect, read exactly 4 bytes, and decode them as an unsigned big-endian count of seconds since 1900.
  • WHOIS: send UserID\r\n, read until the server closes, and find the Tier: field.
  • Redis, RESP2: send INCR usage:<window>:<user> as a two-element array of bulk strings and parse the :n integer reply.
  • The model: an OpenAI-compatible HTTP/JSON endpoint, here a local ELIZA stand-in.

What I built and what was provided

This was Project 1 in a computer networks course. The instructor supplied the backend services, the startup code and the model client. I wrote the seven methods that do the networking and the metering:

Architecture and tradeoffs

The order is forced by data dependencies

The Redis key contains the time window, so the time lookup has to finish first. WHOIS and Redis don't depend on each other, so I submit both to a virtual-thread executor before waiting on either. Waiting on the first future before submitting the second would make the calls sequential and add a full backend round trip to every request. The model is only called after the decision, because protecting it is the reason the gateway exists.

// both tasks are in flight before either result is awaited
var tierFuture    = backends.submit(() -> lookupTier(userID));
var attemptFuture = backends.submit(() -> increment(key));
try {
    tier    = tierFuture.get();
    attempt = attemptFuture.get();
} catch (ExecutionException e) {
    tierFuture.cancel(true);  attemptFuture.cancel(true);
    throw new IOException("Backend call failed", e.getCause());   // → 502
} catch (InterruptedException e) {
    tierFuture.cancel(true);  attemptFuture.cancel(true);
    Thread.currentThread().interrupt();                            // keep interrupt status
    throw new IOException("Backend call interrupted", e);
}

Correctness comes from one atomic operation, not from locks

The gateway keeps no counters. A read-then-write approach (GET, add one, SET) would let two racing requests both read 2, both write 3, and both be admitted. INCR changes the value and returns the new number as one atomic step, so every concurrent request gets its own attempt number and the comparison attempt ≤ limit needs no coordination. The tradeoff is that denied requests are still counted, and a request whose model call fails isn't refunded. The spec accepts both to keep the logic simple.

Two parsing details that would be easy to get wrong

  • Unsigned time. RFC 868 returns an unsigned 32-bit value, and Java's getInt() is signed. Today's timestamps are above 231, so the raw int is negative. I convert it with Integer.toUnsignedLong before dividing by 60.
  • Bytes, not characters. Content-Length counts bytes. The response length is taken from the UTF-8 byte array, not String.length(), and the request body is read with readNBytes(contentLength) because one read() on a TCP stream can return less.

How I verified it

I ran the gateway against the provided services and tested each status path, the tier limits, and the concurrent case:

default user, 5 sequential requests      200 200 200 429 429
registered user, 12 requests             10 × 200, then 2 × 429
20 concurrent requests, one new user     3 × 200, 17 × 429
GET /chat                                405, Allow: POST
POST /other                              404
HTTP/1.0 · bare LF · duplicate header ·
short body · bad X-User-ID · JSON body   400
Redis stopped mid-run                    502 A backend service failed.

The burst is the important result. All 20 requests used a fresh user ID inside one window, and exactly 3 were admitted, the same as the sequential case. That confirms the limit holds under concurrency, not only when requests arrive one at a time.

Bugs I fixed

My first committed draft, f21646a, had two bugs that only show up when you look at the actual bytes on the wire:

  • A client error was reported as a server failure. An invalid X-User-ID threw UnsupportedOperationException. serve() treats anything that isn't a RequestException as a backend failure, so a bad header came back as 502 Bad Gateway, blaming the backends for the client's mistake. Throwing RequestException makes it a 400.
  • Every response was followed by a second one. writeResponse() still ended with the starter's throw placeholder, after flushing. The catch block then wrote a 502 onto the same socket, so a client reading past the first response's Content-Length would find a second, contradictory response. Removing the leftover throw fixed it.

What I would improve next

  • Boundary bursts. With fixed windows, a caller can use its whole quota at 0:59 and again at 1:00. A sliding-window log or a token bucket would remove that double burst.
  • Connection reuse. Each request opens three new TCP connections. Pooling the Redis and WHOIS connections would cut latency under load.
  • Exact error text. My 404, 405 and 429 bodies differ slightly from the spec's wording, for example Rate Limit Exceeded where the spec has Rate limit exceeded. Status codes and headers match.
